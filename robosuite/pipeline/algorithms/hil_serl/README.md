# HIL-SERL For Robosuite

This folder contains a PyTorch-only HIL-SERL implementation integrated with the robosuite simulator.

## What is implemented

- official-style hybrid HIL-SERL learner
  - continuous actor over `action[:-1]`
  - separate `grasp_critic` over the gripper action
  - updates: `critic + grasp_critic + actor + temperature`
- pretrained ResNet-10 visual encoder loaded from:
  - `data/pretrained/resnet10_params.pkl`
- twin-critic ensemble with entropy tuning
- 50 / 50 mixed sampling from:
  - `online_buffer`
  - `demo_buffer`
- HIL-SERL intervention semantics:
  - every executed transition goes to `online_buffer`
  - intervention transitions also go to `demo_buffer`
- robosuite simulator interface with SpaceMouse teleoperation
- sparse reward from robosuite success signal only
- offline demo bootstrap from:
  - `./data/<task>/expert/*.hdf5`
  - optional cached `.pt` transition shards for repeated runs

## Main files

The package is now split into submodules:

- `agent.py`: user-facing HIL-SERL agent API
- `trainer.py`: critic-heavy HIL-SERL update loop
- `models/`
  - `sac.py`: hybrid actor / critic / grasp_critic / alpha update logic
  - `encoders.py`: ResNet-10 and observation encoder stack
- `utils/`
  - `replay_buffer.py`: replay buffers
  - `io.py`: fast transition IO and HDF5 demo conversion
- `envs/`
  - `robosuite.py`: robosuite env, observation, and SpaceMouse intervention bridge
- `common/`
  - `types.py`: shared dataclasses and batch types
  - `utils.py`: tensor / tree / replay helpers

## Simulator interface

The robosuite training entrypoint is:

- `robosuite/pipeline/train_hil_serl.py`

This script follows the official HIL-SERL design more closely:

1. policy acts online in the simulator
2. if the human intervenes with SpaceMouse, the executed action becomes the human action
3. executed transitions always enter the online replay buffer
4. intervention transitions also enter the demo buffer
5. updates sample half-batch from online data and half-batch from demo / intervention data
6. each training cycle runs `cta_ratio - 1` critic-only steps and then one full hybrid update
7. the acting policy snapshot is refreshed every `steps_per_update` learner updates, matching the official actor publish cadence

## Reward design

This integration does not use a reward classifier.

Reward is:
- `1.0` when robosuite reports success through `env._check_success()` or `info["success"]`
- `0.0` otherwise

This keeps the interface aligned with your request and still preserves the sparse-success HIL-SERL setup.

## Demo requirement

You must prepare offline demos before starting the training loop.

The trainer now fails fast if no expert demos are found.
By default it looks for:

- `./data/<task>/expert/*.hdf5`

For example:

- `./data/PandaLift/expert/*.hdf5`

If `data.task_name` is not set, the script infers `<task>` from:

- `<robot><env.environment>`

So the default `Panda + Lift` config resolves to:

- `data/PandaLift/expert`

You can limit how many demo trajectories are loaded with:

- `data.num_trajectories=<N>`

The limit is applied to HDF5 demo trajectories, not just files.

## Demo input format

Supported offline demo inputs:

1. `.pt`
   - fast transition shards generated by this pipeline
2. `.hdf5` / `.h5`
   - expert demos stored under `data/<task>/expert`
   - compatible with the `recover_image.sh` / `backfill_camera_from_states.py` layout
   - supports both HDF5 roots:
     - `demos/...`
     - `data/...`

When an HDF5 file is used, the loader replays the stored simulator states in robosuite and converts them into transitions.
Converted transitions are cached as `.pt` files under:

- `outputs/.../demo_cache/`

This makes repeated training runs much faster.

## Config

Default config file:

- `robosuite/pipeline/config/train_hil_serl.yaml`

Important fields:

- `env.environment`: robosuite task name
- `env.robots`: robot list
- `env.camera_names`: rendered policy cameras
- `env.render_camera`: GUI viewer camera, independent from policy cameras
- `env.proprio_keys`: raw robosuite observation keys to flatten into `state`
- `algorithm.encoder.*`: visual / proprio encoder settings
- `algorithm.sac.*`: SAC hyperparameters
- `algorithm.trainer.cta_ratio`: critic-heavy update ratio
- `algorithm.trainer.steps_per_update`: actor snapshot refresh interval
- `data.task_name`: optional override for `data/<task>/expert`
- `data.num_trajectories`: how many expert trajectories to load
- `data.demo_paths`: optional explicit file override
- `intervention.enabled`: enable SpaceMouse intervention
- `runtime.checkpoint`: resume or evaluation checkpoint path
- `runtime.viewer_enabled`: turn the GUI mirror on or off
- `runtime.viewer_async`: render GUI in a background thread instead of the control loop
- `runtime.viewer_fps`: GUI refresh rate for the mirrored viewer

## GUI Performance

The control environment is now always headless.

When `runtime.interactive=true` and `runtime.viewer_enabled=true`, the GUI is driven by a separate mirrored robosuite env.
The training env publishes simulation snapshots, and the viewer env renders them on its own cadence.

This avoids paying MuJoCo viewer cost on every control step and makes SpaceMouse teleoperation much more responsive.

## How to run

There is only one training workflow in this robosuite port:

1. prepare offline demos under `data/<task>/expert`
2. start the training script
3. optionally enable SpaceMouse intervention during the online loop

So:

- `offline demos` are required input data before training starts
- `SpaceMouse intervention` is an optional behavior during the same training loop

They are not two separate training modes.

### 1. Prepare offline demos

By default the trainer automatically reads demos from `data/<task>/expert/*.hdf5`

### 2. Start training

Use the helper script:

```bash
bash robosuite/pipeline/scripts/train_hil_serl.sh
```

The script only exposes a few common knobs:

- `ENVIRONMENT`
- `ROBOTS`
- `DEMO_TASK_NAME`
- `NUM_TRAJECTORIES`
- `INTERVENTION_ENABLED`
- `RESUME`
- `CHECKPOINT`

Example:

```bash
ENVIRONMENT=Lift \
DEMO_TASK_NAME=PandaLift \
NUM_TRAJECTORIES=20 \
bash robosuite/pipeline/scripts/train_hil_serl.sh
```

If you want SpaceMouse-enabled human intervention during training, keep:

```bash
INTERVENTION_ENABLED=true
```

If you want purely autonomous online collection after loading demos, set:

```bash
INTERVENTION_ENABLED=false
```

If you prefer to run Python directly:

```bash
/home/dodo/miniconda3/envs/daggar/bin/python -m robosuite.pipeline.train_hil_serl \
  env.environment=Lift \
  env.robots='[Panda]' \
  data.task_name=PandaLift \
  data.num_trajectories=20 \
  intervention.enabled=true
```

### 3. Resume training

To resume automatically from the latest run:

```bash
RESUME=true bash robosuite/pipeline/scripts/train_hil_serl.sh
```

To resume from a specific checkpoint:

```bash
CHECKPOINT=/absolute/path/latest.pt RESUME=true \
bash robosuite/pipeline/scripts/train_hil_serl.sh
```

### 4. Deterministic evaluation rollout

Edit the checkpoint path in:

- `robosuite/pipeline/scripts/eval_hil_serl.sh`

Then run:

```bash
bash robosuite/pipeline/scripts/eval_hil_serl.sh
```

Or directly:

```bash
/home/dodo/miniconda3/envs/daggar/bin/python -m robosuite.pipeline.train_hil_serl \
  runtime.max_steps=2000 \
  runtime.interactive=false \
  runtime.eval_deterministic=true \
  intervention.enabled=false \
  runtime.checkpoint=/absolute/path/latest.pt
```

## Output files

Checkpoints are written as fast `.pt` files under:

- `outputs/hil_serl/<run_name>/checkpoints/`

The latest checkpoint stores:

- model weights
- alpha optimizer state
- online replay buffer
- demo replay buffer
- global step metadata

This means resume is self-contained and does not depend on separate replay pickle files.

## Notes

- SpaceMouse reset input is treated as an episode reset request during training.
- If you want pure autonomous training, set `intervention.enabled=false`.
- If you want pretrained visual backbones, switch `algorithm.encoder.encoder_type=resnet-pretrained`.
